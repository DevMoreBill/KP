# Новая миграция базы

Схема меняется ТОЛЬКО миграцией в `app/storage.py`; рабочую базу пользователя руками не трогать.

1. **Имя**: следующее по порядку в `MIGRATIONS`, вида `'2027-NN-коротко'` (посмотреть последнее). Добавлять в КОНЕЦ списка.
2. **Запись**: `('2027-NN-…', """up""", """down""")`:
   - up — `CREATE TABLE IF NOT EXISTS …`, `CREATE INDEX IF NOT EXISTS …`, `ALTER TABLE t ADD COLUMN x …;` (лишний ADD/DROP
     пропускается сам — `Store._idempotent`), триггеры `CREATE TRIGGER IF NOT EXISTS`;
   - down — обратное: `DROP TABLE IF EXISTS`, `DROP INDEX IF EXISTS`, `ALTER TABLE t DROP COLUMN x;`, `DROP TRIGGER IF EXISTS`;
   - существующие данные не удалять и не переписывать — только добавлять.
3. **Заполнение данных** (если новые столбцы считаются из старых): функция `_fill_<что>(st, c)` рядом с прочими `_fill_*`,
   только через `c` (та же транзакция), SQL с параметрами `?`; строка в `MIGRATION_FILL`. Схема, данные и отметка в kv «schema»
   идут одной транзакцией (`_atomic_script`): сбой — база как была.
4. **Код**: запросы к новым таблицам и столбцам — в методах `Store` или в классе раздела (ООП), SQL только с `?`, имена
   таблиц и полей не из ввода.
5. **Проверка** в `tests/` (на `TempStore`/`Stand` с вымышленными данными):
   - новая база: миграция применена, таблица/столбец есть, заполнение верное;
   - «база прежней версии»: `Schema.down_to(store, '<имя>')` (tests/kit.py) → таблиц нет → `migrations_up()` → всё на месте,
     данные сохранены и заполнены. Не перечислять поздние миграции по именам — для этого `Schema.down_to`;
   - откат: `store.migration_down('<имя>')` последней миграции убирает только её.
6. `python3 tests/run_all.py --strict` (в т. ч. `test_audit_fixes`: откат только последней миграции), затем выпуск — `/vypusk`.
