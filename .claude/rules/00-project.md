# Проект «Конструктор КП ПНЕВМОТЕХ» — правила разработки

## Стек и ограничения
- Сервер: Python 3, **только стандартная библиотека** (`app/*.py`, `http.server`, SQLite через `sqlite3`). Не добавлять
  зависимости из PyPI/npm без явной просьбы — программа собирается в один EXE (PyInstaller, `kp.spec`,
  `.github/workflows/build-exe.yml`). Новый модуль сервера — добавить в `hiddenimports` в `kp.spec`.
- Клиент: JavaScript без сборщика и фреймворков (`app/web/js/**`; переписанное — ES-модули, старое — скрипты с `'use strict'`),
  CSS — `app/web/css/*.css`, подключение — `app/web/index.html`.
- Интерфейс, сообщения, комментарии, журнал изменений, коммиты — **на русском**.

## ООП — главное правило (решение владельца проекта)
- Новый код — только в классах. Сервер: классы с состоянием (`FeatureAccess(store)`, `DealTrack(store)`, `Mailer(store)`)
  или со статическими методами (`OfferTerm.until`, `Val.day`); маршруты — методы контроллеров `web_api.py` (`@route`).
  Клиент: классы со статическими или обычными методами (`Drafts`, `Presets`, `NewKp`, `KpLoader`, `KpDate`, `Steps`,
  `ClientCard`, `MyDay`), окна — через `Modal`. Новых глобальных функций и процедурных модулей не заводить.
- Один класс — одна ответственность; данные и действия над ними — вместе; служебное — «_метод»; константы — атрибуты класса.
- Изменяя старый процедурный код, переносить затронутую часть в класс по месту (без переписывания всего файла разом).

## Оформление кода (решение владельца 19.10: «переписать по современным правилам, код идеально вылизан»)
- Переписывание — по частям, каждая часть — отдельный выпуск с тем же поведением до миллиметра и рубля (слепки:
  `tests/js/station_golden.js`, `tests/js/deal_golden.js`); порядок — компоновка станций, сервер, остальной интерфейс.
- Интерфейс — ES-модули без сборщика (`import`/`export`, в `index.html` — `type="module"`; с 3.169.0 переведён весь): папки
  `features/*/`, `ui/`, `core/` — по классу на ответственность, `index.js` папки кладёт классы в `globalThis` и вешает
  обработчики `document` в `listen()`. Порядок модулей в `index.html`: `core/index.js` первым, затем `ui/index.js`, затем
  разделы; `main.js` (`App`) — последним. Обычными скриптами остаются только то, что нужно до модулей: `core/util.js`
  (`$`, `esc`, `uid`, `today`), `core/defaults*.js` (реестр «Значений программы» — порядок групп), `core/state.js` (`S` и общие
  `let`, которые присваивают модули: `catCache`, `EDIT`, `TYPES`, `STEP`, `GEO_EXTRA`, `CLIENTS`, `MGRS` …), `core/lists.js`
  (`LISTS`), `features/help.js` (данные версий — их правит `/vypusk`), `boot.js`, `docx/kpgen.js` (сторонний). Новую общую
  переменную, которую присваивают разные модули, — только в `core/state.js`. Старые имена функций — тонкие мосты в
  `core/legacy.js`, `ui/legacy.js`, `kp/legacy.js`, `catalog/legacy.js` (без логики; новый код зовёт методы классов).
  Массивы модуля в «Списках и выборах» — `late: true` в `core/lists.js` и `LISTS.ready([...])` в `index.js` модуля.
- Проверка обращений `Класс.член` после переименований — ESLint `kp/no-undef` (имена) и сверка членов классов; сверка
  поведения — слепки (`tests/js/*golden*`) и разметка страниц прогона (`KP_PROGON_DOM=1 tests/ui/progon.py` рядом со
  снимками кладёт `.html` — сравнить с прогоном прежней версии).
- Вместо цепочек `if/else` и вложенных `?:` — таблицы соответствий, ранний выход, маленькие методы с говорящими
  именами, шаги-конвейеры; одна функция — одна задача.
- Комментарии — только короткое «почему», если из кода не очевидно; решения владельца, даты, нормы и история — в
  `.claude/rules/*.md` и инженерных правилах программы (`stations.json`), не в коде.
- Подписи типов: в переписанном Python — аннотации (`def f(x: int) -> str`), в переписанном JS — JSDoc у открытых
  методов. Не переписанный код — как был.
- Инструменты (только для разработки, в EXE не входят): Ruff (`pyproject.toml`; переписанные модули — `ruff check` и
  `ruff format`), ESLint со строгими правилами и Prettier (`.prettierrc.json`) для ES-модулей; список переписанных
  Python-модулей — `tests/code_style.json`. Всё запускает `tests/run_all.py` и CI.
- (20.10, «чистый код» по testdriven.io/blog/clean-code-python, решение владельца «делай всё») Имена — говорящие, не
  короче 3 знаков (кроме индексов `i j k`, координат `x y z x0 x1 x2 y0 y1 y2 z0 z1 z2 dx dy dz` и `id ok kw el gl db of _`; словарь геометрии станции — `ox oy` начало помещения, `Li Wi Hi` внутренние, `Le We He`
  наружные длина, ширина, высота; на грани и стене `u v u0 u1 v0 v1 du dv` — вдоль и по высоте); одно
  понятие — одно слово; без логических флагов в параметрах (вариант — объектом `{…}` или отдельный метод; в Python — отдельный метод, перечисление
  `Enum` вроде `data_file.Load` или объект вроде `features.Viewer`); без
  «магических чисел» в логике (константа класса или модуля, правило `stations.json`; на сервере проверяет Ruff PLR2004); общие помощники — один раз (`Mm.text`,
  `Mm.dec` для мм и десятичных); у открытых методов ES-модулей — JSDoc. Проверки: ESLint `id-length` и `kp/jsdoc` для
  переписанных папок, `tests/test_names.py` для Python (имена — список «names», флаги — «flags» в `tests/code_style.json`),
  mypy для сервера (`tests/code_style.py`).
- Формат коммитов — как в истории репозитория (`3.x.y: что сделано` + список), а не `feat:/fix:`.

## База данных
- Схема меняется только миграциями в `app/storage.py` (атомарно, `MIGRATION_FILL`), без ручной правки рабочей базы
  пользователя. Совместная правка — номер ревизии (`rev`, заголовок `X-KP-Rev`, ответ 409).

## Безопасность
- SQL — только с параметрами (`?`), поиск по `LIKE` — через `like_arg`; имена таблиц и полей не собирать из ввода.
- Ввод проверять на сервере, на границе (как `UserPrefs.save`, `Val`): известные поля, длина, формат; ошибка — `ValueError`
  с понятным текстом для пользователя, без путей, SQL и трассировки.
- В HTML всё пользовательское и из базы — через `esc(...)`; `innerHTML` с сырыми данными не собирать.
- Админка: изменения — только с сессией администратора и токеном `X-CSRF-Token` (`admin.is_admin`); новые маршруты
  изменения данных — так же. Пути к файлам из запроса — не выходить за свою папку.
- Ключи API, пароли и токены — не в репозиторий и не в журналы; базы и выгрузки пользователя (`*.sqlite3`, `kp*.zip`) — тоже.

## Проверки перед коммитом
- `python3 tests/run_all.py` — pyflakes, ESLint для `app/web/js` (`eslint.config.mjs`, необъявленные имена), наборы `tests/` на стенде
  со сгенерированной базой; то же CI делает при каждой отправке, и EXE собирается только после этого. Новая функция сервера — проверка
  в `tests/` (на `kit.Stand`/`SampleData`, без данных пользователя). Сценарии Playwright — на копии базы (не на рабочей).
- Версия: `app/version.py` + `APP_VERSION` и журнал в `app/web/js/features/help.js`, README — навык `/vypusk`
  (`.claude/skills/vypusk/vypusk.py` ставит номер и проверяет записи).
- Мелкая правка — `python3 tests/run_all.py --changed` (только затронутое); перед выпуском — полный `--strict`. Интерфейс —
  `/progon` (`tests/ui/progon.py`); схема базы — `/migraciya`; безопасность и расчёты — помощники `proverka-bezopasnosti`,
  `proverka-raschetov` (`.claude/agents`). Хуки `.claude/hooks`: `guard.py` не даёт записать базы, выгрузки, ключи и `app/data/`,
  `lint.py` проверяет файл сразу после правки.
