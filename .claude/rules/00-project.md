# Проект «Конструктор КП ПНЕВМОТЕХ» — правила разработки

## Стек и ограничения
- Сервер: Python 3, **только стандартная библиотека** (`app/*.py`, `http.server`, SQLite через `sqlite3`). Не добавлять
  зависимости из PyPI/npm без явной просьбы — программа собирается в один EXE (PyInstaller, `kp.spec`,
  `.github/workflows/build-exe.yml`). Новый модуль сервера — добавить в `hiddenimports` в `kp.spec`.
- Клиент: JavaScript без сборщика и фреймворков (`app/web/js/**`; переписанное — ES-модули, старое — скрипты с `'use strict'`),
  CSS — `app/web/css/*.css`, подключение — `app/web/index.html`.
- Интерфейс, сообщения, комментарии, журнал изменений, коммиты — **на русском**.

## ООП — главное правило (решение владельца проекта)
- Новый код — только в классах. Сервер: классы с состоянием (`FeatureAccess(store)`, `DealTrack(store)`, `Mailer(store)`)
  или со статическими методами (`OfferTerm.until`, `Val.day`); маршруты — методы контроллеров `web_*.py` (`@route`; порядок поиска — `web_api.CONTROLLERS`; отказ — `raise Forbidden(текст)` /
  `NotFound(текст)`, ответ 403 / 404 формирует `Router`).
  Клиент: классы со статическими или обычными методами (`Drafts`, `Presets`, `NewKp`, `KpLoader`, `KpDate`, `Steps`,
  `ClientCard`, `MyDay`), окна — через `Modal`. Новых глобальных функций и процедурных модулей не заводить.
- Один класс — одна ответственность; данные и действия над ними — вместе; служебное — «_метод»; константы — атрибуты класса.
- Изменяя старый процедурный код, переносить затронутую часть в класс по месту (без переписывания всего файла разом).

## Оформление кода (решение владельца 19.10: «переписать по современным правилам, код идеально вылизан»)
- Переписывание — по частям, каждая часть — отдельный выпуск с тем же поведением до миллиметра и рубля (слепки:
  `tests/js/station_golden.js`, `tests/js/deal_golden.js`); порядок — компоновка станций, сервер, остальной интерфейс.
- Интерфейс — ES-модули без сборщика (`import`/`export`, в `index.html` — `type="module"`): папки `features/*/`, `ui/`, `core/` —
  по классу на ответственность. Каждый файл подключает нужное `import` — общих имён между файлами нет (с 3.170.0: без
  `globalThis` и без «склеек» прежних имён). `index.js` папки только вешает обработчики `document` (`listen()`) и регистрирует
  списки и значения (метку версии каждому модулю ставит карта импорта `WebIndex` — новые файлы нигде прописывать не нужно); порядок в `index.html`: `core/index.js` первым (он подключает `state.js` → «Значения программы» →
  `lists.js`), затем `ui/index.js`, разделы, `main.js` (`App`) — последним. Обычные скрипты — только `boot.js` (тема до
  отрисовки) и `docx/kpgen.js` (`KPGen`: общий с проверками в Node и скелетом шаблона КП). Разделы «по требованию»
  (`tz-out/`, `rules-doc/`) не импортируются статически — только `LazyJs.load('…/index.js')`, классы — из его результата.
- Общие данные — у класса-владельца, а не в общих переменных: открытое КП — `S` (`core/state.js`, `export let`, меняется только
  `KpState.replace(…)`), каталог — `Catalog.cache`, открытая карточка — `ItemEditor.current`, правка позиции каталога —
  `CatalogEditor.session`, раздел формы — `Steps.current` (разделы — `KpForm.step()`), типы оборудования — `EquipTypes.list`/`.builtin`, клиенты —
  `ClientStore.list`/`.total`, менеджеры — `Managers.list`, «Значения программы» — `DefRegistry.value/num`, `DefRegistry.srv`,
  версия — `AppVersion.current`. Модуль, который выполняет код при загрузке, не должен ждать модулей, подключающих его
  (циклы `import`): реестр значений `core/defaults.js` и условия `core/conditions.js` — без тяжёлых зависимостей.
  (30.10, п. 29 отчёта аудита) `core/` — нижний слой: не подключает `features/` и `ui/` (ESLint `no-restricted-imports`);
  разделы подписываются на события `kp:features`, `kp:theme`, `kp:saved`, `kp:password`, `kp:unauthorized` и подключаются в
  своём `index.js`: `LISTS.ready({ключ: () => массив})`, `DefRegistry.options`, `KpState.onItem/onPersist/paused`, `Api.who`;
  экземпляр, которому нужны другие модули, создаётся при первом обращении (`CatalogWindow.win`), а не при загрузке.
  (30.10, циклы импортов, этап 1) Слои: `core/` ← разделы `features/` ← форма КП `ui/` ← `main.js`; разделы не подключают
  `ui/` (ESLint `no-restricted-imports`): перерисовать форму, открытый шаг, выбрать или открыть шаг, боковая панель,
  «что мешает сохранить» — `KpForm` (`core/kp-form.js`, форму подключает `ui/index.js` — `KpForm.connect`), телефонная
  раскладка — `PhoneLayout.active()`, общие виджеты — в `core/` (`UiKit`, `DatePicker`/`WorkCalendar`, данные тендера
  `Tender`, `CondMemory`); раздел, которому нужна форма, просит через `KpForm`, а не импортирует её. (30.10, этап 2) КП
  (`features/kp`) не подключает кабинет (`features/crm`, построен поверх КП): открыть кабинет или сделку, сделки и стадии —
  `CabinetLink` (`core/cabinet-link.js`, подключает `features/crm/index.js`); `KpDate`, `CrmFmt`, `DateChips` — в `core/`.
- Проверки: ESLint `no-undef` (забытый `import` — ошибка проверки), слепки (`tests/js/*golden*`), проверки в Node — через
  `tests/js/web.js` (минимальное окружение браузера; классы модулей доступны по имени только в проверках; подмена — методами
  настоящих классов: `Attrs.of = …`, `Catalog.cache = […]`, `KpState.replace(…)`), разметка страниц прогона
  (`KP_PROGON_DOM=1 tests/ui/progon.py` кладёт `.html` рядом со снимками — сравнить с прогоном прежней версии; правка стилей —
  ещё и `KP_PROGON_GEOM=1`: место, размер, кегль, цвета каждого элемента и размеры открытых окон, `*.geom.json`; классы в окне
  страницы прогон открывает сам, только для своих проверок). Данные-файлы (`help.js`, `defaults-srv.js`, `defaults-kp.js`) —
  в `.prettierignore`: их компактный вид читают `/vypusk` и проверки.
- (30.10, п. 29 отчёта аудита) Окна в стилях: размер окна раздела — в слое `@layer win`, режим окна (вкладка, телефон, лист
  снизу, вход в «Настройки», во весь экран для предпросмотра) — в `@layer win-mode` (порядок слоёв — в начале `base.css`):
  режим перекрывает размер без !important; новое окно задаёт размер в `@layer win`. Размер и место, выбранные
  пользователем (потянул, перенёс, запомнено), — `WinSize` (`core/win-size.js`, свойства `--dlg-w/-h/-x/-y`), не
  `style.width`; значения, которые JS вычисляет для сетки, — тоже свойствами (`--cab-cols`, `--lay-cols`). !important —
  только печать, разметка библиотеки показа Word и правила-политики (сенсорный экран, перетаскивание, «меньше движения»,
  `[hidden]` формы) — список с причинами в `tests/test_css_important.py`; общие компоненты (`.lnk`, `.sw`, `.seg`, `.mtog`,
  `.ck`, `.chk-chip`) — в `base.css`.
- Вместо цепочек `if/else` и вложенных `?:` — таблицы соответствий, ранний выход, маленькие методы с говорящими
  именами, шаги-конвейеры; одна функция — одна задача.
- Комментарии — только короткое «почему», если из кода не очевидно; решения владельца, даты, нормы и история — в
  `.claude/rules/*.md` и инженерных правилах программы (`stations.json`), не в коде.
- Подписи типов: в переписанном Python — аннотации (`def f(x: int) -> str`), в переписанном JS — JSDoc у открытых
  методов. Не переписанный код — как был.
- Инструменты (только для разработки, в EXE не входят): Ruff (`pyproject.toml`; переписанные модули — `ruff check` и
  `ruff format`), ESLint со строгими правилами и Prettier (`.prettierrc.json`) для ES-модулей; список переписанных
  Python-модулей — `tests/code_style.json`. Всё запускает `tests/run_all.py` и CI.
- (20.10, «чистый код» по testdriven.io/blog/clean-code-python, решение владельца «делай всё») Имена — говорящие, не
  короче 3 знаков (кроме индексов `i j k`, координат `x y z x0 x1 x2 y0 y1 y2 z0 z1 z2 dx dy dz` и `id ok kw el gl db of _`; словарь геометрии станции — `ox oy` начало помещения, `Li Wi Hi` внутренние, `Le We He`
  наружные длина, ширина, высота; на грани и стене `u v u0 u1 v0 v1 du dv` — вдоль и по высоте); одно
  понятие — одно слово; без логических флагов в параметрах (вариант — объектом `{…}` или отдельный метод; в Python — отдельный метод, перечисление
  `Enum` вроде `data_file.Load` или объект вроде `features.Viewer`); без
  «магических чисел» в логике (константа класса или модуля, правило `stations.json`; на сервере проверяет Ruff PLR2004); общие помощники — один раз (`Mm.text`,
  `Mm.dec` для мм и десятичных; на сервере — `Clock`, `Inn`, `Money`, разбор числа `Num.parse`); у открытых методов ES-модулей — JSDoc. Проверки: ESLint `id-length` и `kp/jsdoc` для
  переписанных папок, `tests/test_names.py` для Python (имена — список «names», флаги — «flags» в `tests/code_style.json`),
  mypy для сервера (`tests/code_style.py`).
- Формат коммитов — как в истории репозитория (`3.x.y: что сделано` + список), а не `feat:/fix:`.

- (23.10, решение владельца) Каждая новая функция — свой выключатель: ключ в `app/features.py` (`FEATURES`, адреса — `ROUTES`,
  «только вместе с» — `NEEDS`) и в `app/web/js/core/features.js` (`needs` тот же), подробная инструкция «Где · Как пользоваться ·
  Выключено» — в `app/web/js/core/feature-help.js`; выключенная функция прячется в интерфейсе и закрыта на сервере, данные не
  удаляются. Проверка — `tests/test_features_help.py` (`needs` сверяется в обе стороны с 3.226.6). Новое действие журнала
  (`admin.log`) — подпись в `AuditLabels.ACT` (`admin-core.js`), проверка `test_audit_3010.JournalLabels`.

## База данных
- Схема меняется только миграциями в `app/storage.py` (атомарно, `MIGRATION_FILL`), без ручной правки рабочей базы
  пользователя. Совместная правка — номер ревизии (`rev`, заголовок `X-KP-Rev`, ответ 409).

## Безопасность
- SQL — только с параметрами (`?`), поиск по `LIKE` — через `like_arg`; имена таблиц и полей не собирать из ввода.
- Ввод проверять на сервере, на границе (как `UserPrefs.save`, `Val`): известные поля, длина, формат; ошибка — `ValueError`
  с понятным текстом для пользователя, без путей, SQL и трассировки; текст чужого исключения пользователю и в состояние
  задач — только через `server_log.ErrorText.of(exc)` (пути на диске сервера — многоточием; 30.10, аудит).
- В HTML всё пользовательское и из базы — через `esc(...)`; `innerHTML` с сырыми данными не собирать.
- Админка: изменения — только с сессией администратора и токеном `X-CSRF-Token` (`admin.is_admin`); новые маршруты
  изменения данных — так же. Пути к файлам из запроса — не выходить за свою папку.
- Ключи API, пароли и токены — не в репозиторий и не в журналы; базы и выгрузки пользователя (`*.sqlite3`, `kp*.zip`) — тоже.

## Проверки перед коммитом
- `python3 tests/run_all.py` — pyflakes, ESLint для `app/web/js` (`eslint.config.mjs`, необъявленные имена — забытый `import`), наборы `tests/` на стенде
  со сгенерированной базой; то же CI делает при каждой отправке, и EXE собирается только после этого. Новая функция сервера — проверка
  в `tests/` (на `kit.Stand`/`SampleData`, без данных пользователя). Сценарии Playwright — на копии базы (не на рабочей).
- Версия: `app/version.py` + `APP_VERSION` и журнал в `app/web/js/features/help.js`, README — навык `/vypusk`
  (`.claude/skills/vypusk/vypusk.py` ставит номер и проверяет записи).
- (26.10, решение владельца: «каждая сборка отнимает час даже при минимальных правках — придумай тестирование с грамотным
  распределением ресурсов»; уточняет 23.10) Четыре уровня — каждая проверка один раз и только по затронутому:
  1) **правка** — `python3 tests/run_all.py --changed` (карта `Changed`: сервер — наборы с этим модулем, JS — проверки в Node и
     кнопок, станции — только при правке станций, CSS — статические; ≈ 10–60 с) и снимок изменённого окна;
  2) **выпуск** (коммит с версией) — то же + `python3 tests/ui/progon.py --changed` (`ProgonPlan`: этапы — разделов, файлы
     которых менялись с прошлой сборки (метка `v*`), режимы — JS → ПК, вёрстка → ПК и телефон, цвета/тема → и тёмные, общее
     (`core/`, `ui/`, `main.js`, общие стили, сам прогон) → все этапы; только сервер — без прогона); полный набор `tests/`
     локально НЕ повторять — его делает CI при отправке тремя параллельными частями (`run_all.py --shard=K/3`, время частей —
     `tests/suite_times.json`, обновлять при заметном росте наборов);
  3) **сборка** («собери») — локально ничего не перезапускать: коммит, уже проверенный CI при отправке, собирается без
     повторных проверок (задание `gate` в `build-exe.yml`), сборка сама проверяет EXE (запуск, обновление, сервер отдела);
  4) **полный** — `run_all.py --strict` и прогон всех режимов (`--modes pc,pcd,ph,phd,tab`) — только при большой переделке
     интерфейса, по просьбе владельца или примерно раз в 10 выпусков; нагрузочный стенд (20 менеджеров) — при правке ядра
     сервера (`kp_server`, `storage`, `web_api` и `web_*`) по скорости.
  Прогон — свой стенд на режим (режимы не мешают друг другу, повторять на прежней версии не нужно). Интерфейс —
  `/progon` (`tests/ui/progon.py`); схема базы — `/migraciya`; безопасность и расчёты — помощники `proverka-bezopasnosti`,
  `proverka-raschetov` (`.claude/agents`). Хуки `.claude/hooks`: `guard.py` не даёт записать базы, выгрузки, ключи и `app/data/`
  и добавить в код голый except, eval/exec, pickle, shell=True, SQL через f-строку, var, new Function, document.write
  (`Danger`), `lint.py` проверяет файл сразу после правки.
- (30.10, аудит) Гейт безопасности — в имеющихся проверках (отдельного quality.yml нет): Ruff — правила S в `pyproject.toml`,
  исключения только узкие (файл + правило) и с причиной, где доказано по коду; ESLint — `no-eval`, `no-implied-eval`,
  `no-new-func` (кроме `docx/kpgen.js`), `eqeqeq`; `kp/esc-html` (разметка без `esc`) и сложность обычных скриптов —

  «Класс.метод(…)» импортированного класса интерфейса — метод есть у класса (`tests/js/static_calls.js`). Подавление
