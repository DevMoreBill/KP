# Конструктор КП ПНЕВМОТЕХ

Программа для составления технико-коммерческих предложений (DOCX): каталог оборудования, расчёт цен,
журнал КП, контрагенты, шаблоны оформления. Собирается в **один EXE** — на компьютерах Python не нужен.
Работает на одном компьютере или как **сервер отдела** (одна база на всех, сотрудники — в браузере).

Инструкция для пользователей — [Инструкция.txt](Инструкция.txt), для администратора сервера отдела —
[server-setup/Как устроен сервер отдела.txt](server-setup/Как%20устроен%20сервер%20отдела.txt).

## Где взять EXE

GitHub → **Releases** → последний выпуск `v<версия>`: `Конструктор КП.exe`, комплект `Конструктор КП.zip`
(EXE + server-setup + Инструкция) и патч `Обновление КП.zip`. Промежуточные сборки — Actions → «Сборка EXE для Windows» → Artifacts
(хранятся неделю, при исчерпанной квоте хранилища не выкладываются).

Одна сборка — Windows 8.1 / 10 / 11, 64-бит (Python 3.12). Решение серверное: программа стоит на сервере отдела,
сотрудники работают в браузере; сборки для Windows 7 нет.

Каждая сборка проверяется на Windows: запуск, база SQLite, каталог, шаблоны, типы, новый номер КП, сохранение DOCX, выход.
Релиз с файлами — тег `v*` или Actions → «Сборка EXE для Windows» → Run workflow с отметкой «release» (тег `v<версия из app/version.py>` ставится сам).

## Установка в C:\KP и обновления патчем

Постоянная папка программы — `C:\KP`. Полный комплект ставится один раз: `install\Установить в C KP.cmd`
(права администратора; перенос данных из прежней папки, ярлык, переключение сервера отдела на `C:\KP`).

Дальше каждое исправление — артефакт **«Обновление КП (патч)»** (`Обновление КП.zip`, ≈1 МБ, один на обе сборки):
`Установить обновление.cmd` останавливает программу и сервер отдела, кладёт код и интерфейс новой версии в
`C:\KP\update` (`update\version.json`, `update\app\*.py`, `update\app\web\…`, `update\templates\…`) и запускает
программу снова. Данные не затрагиваются.

Как это работает: точка входа EXE — `app/launcher.py`. Если в `update\version.json` версия новее встроенной
(`app/version.py`), модули `app\*.py` загружаются из `update\app` раньше встроенных, интерфейс и заводские шаблоны —
тоже оттуда (`config.APP_DIR`, `UPDATE_DIR`). Новый полный EXE с той же или более новой версией игнорирует старый патч.
Патч может импортировать модули стандартной библиотеки Python, встроенные в EXE: с 3.51 в `kp.spec` — список `STDLIB`
с запасом (почта IMAP/POP и MIME, XML, HTML, HTTP, журналы, архивы, точные вычисления, потоки, сравнение текстов, TOML и др., +0,4 МБ);
не входят tkinter, unittest, pydoc, multiprocessing, xmlrpc, asyncio. Перед выпуском увеличивайте `VERSION` в `app/version.py`.

**Обновление не запустилось — возврат к прежней версии** (EXE с 3.51): `launcher.py` — класс `Launcher`. Ошибка в коде обновления
до начала работы (импорт, подготовка при запуске) или неудачная самопроверка (`app_update.StartCheck`: новая версия должна ответить
на `/api/version`, `/api/ping` и `/`; до этого `kp_server.STARTED = False`, браузер не открывается) — папка `update` → `update.failed`,
`update.prev` → `update` (если она новее EXE), запись `update-failed.json` рядом с программой (версия, причина, трассировка),
модули обновления выгружаются, и программа запускается заново встроенным `Restarter` (≈3–4 с). Ошибки окружения (база повреждена
или занята, нет места, нет прав — `StartCheck.code_error`) прежняя версия встретила бы так же — тогда отката нет, обычное сообщение.
Запущенная версия переносит запись в историю установок (`Updater.absorb_failures`), «Обновления» и «Требует внимания» показывают
причину, пока работает версия старше неудачной. Сам `launcher.py` встроен в EXE и патчем не меняется: самопроверка и передача
ошибки запуска включаются, только если EXE умеет вернуть прежнюю версию (`KP_UPDATE_FALLBACK`, `StartCheck.armed()`), —
на прежнем EXE патч запускается как раньше.
CI проверяет: EXE с папкой `update` версии 99.0.0 берёт код и интерфейс из неё, с устаревшей — нет; после установки из «Настроек»
сломанного обновления (ошибка при запуске — 99.0.2, ответ 500 на самопроверке — 99.0.3) программа сама возвращается к 99.0.1.

**Ночные обновления** (по желанию, EXE с 3.51): «Настройки → Обновления» → «Ночные обновления» — выключено, «только исправления»
(новая версия той же ветки: 3.52.0 → 3.52.1) или «все новые версии», время — с выбранного часа (по умолчанию 3:00) два часа.
`app_update.NightUpdate`: проверка раз в полчаса (`maintenance.Background.every`), ставит, только если последние 15 минут не было
изменяющих запросов (`NightUpdate.touch` в `kp_server.Handler`), одна попытка за ночь, версия из `update.failed` сама не ставится;
установка — `Updater.download_latest` (копия базы перед обновлением, история «ночное обновление»), затем `Restarter.restart`. Итог —
kv `update.nightLast`, строка в «Обновлениях», событие в письме администратору; не запустилась — возврат к прежней версии (см. выше).

`app/web` (обновить страницу — F5); сервер — в `app/*.py` (перезапуск `python app/kp_server.py`).

## Данные

| Где | Что |
|---|---|
| `data/img/` | изображения по папкам латиницей: `compressors/screw-compressors/dalgakiran/dalgakiran-tidy-n-3__<отпечаток>.jpg`, логотипы — `logos/<производитель>__<отпечаток>.png`; одинаковые хранятся один раз |
| `data/kp.sqlite3` | каталог, журнал КП и нумерация, контрагенты, проверки Checko, ключи API, свои типы оборудования; журнал действий (`audit`), корзина (`trash`), правки на модерации (`pending_edits`) |
| `data/backup/` | копии базы перед обновлением программы и каталога, перед загрузкой базы и импортом в «Настройках» — архивы `kp-…-before-….zip` |
| `data/backup/auto/` | ежедневные копии базы — архивы `kp-ГГГГ-ММ-ДД.zip` (внутри `kp.sqlite3`; копия проверена `integrity_check` до сжатия и по контрольным суммам после): 7 последних дней, по одной на 4 недели и на 12 месяцев |
| `data/backup/audit-archive/` | записи журнала действий старше срока хранения (по умолчанию 2 года), `audit-ГГГГ.jsonl.gz` |
| `data/img/` | фото и логотипы (имя файла = хеш содержимого, повторы не хранятся) |
| `Коммерческие предложения/<Фамилия>/` | готовые КП `.docx` |
| `templates/` | шаблоны КП |
| `settings.json` | `mode` (`local` / `server`), `port` (17845), `dataDir` (папка данных на **локальном** диске), `docsShare` (сетевой путь к папке КП для сотрудников) |

Каждый день при первом запуске (и раз в сутки, пока работает сервер отдела) программа сама делает копию базы
в `data/backup/auto`, проверяет её, сжимает в архив ZIP (в 15–20 раз меньше: база 271 МБ → 16 МБ) и удаляет лишние старые;
прежние копии без сжатия (`.sqlite3`) перепаковываются в ZIP сами; раз в месяц база сжимается (`VACUUM`) и проверяется.
Состояние и кнопки «Создать копию сейчас», «Сжать и проверить базу», срок хранения журнала действий, поиск и удаление
изображений без ссылок — «Настройки» → «Копии и база». Вручную — «Копии и база» (вся база или разделы в JSON, файл базы архивом .zip) или
`server-setup/5. Резервная копия базы.bat` (согласованная копия базы «на ходу» + фото).
Переход с прежних версий (данные в JSON-файлах `data/catalog`, `data/kp`…) — автоматически при первом запуске;
старые папки остаются нетронутыми как резервная копия. Изменения структуры базы — обратимые миграции
(`MIGRATIONS` в `app/storage.py`; откат — «Настройки» → «Пароль и доступ»); миграция и отметка о ней записываются одной транзакцией.

Совместная работа: у КП, позиций каталога, контрагентов, менеджеров и поставщиков есть номер правки (`rev`). Сохранение
передаёт номер, с которого начинали (`X-KP-Rev`); если запись успели изменить, сервер отвечает 409, и программа спрашивает,
перезаписать ли (у КП прежний вариант остаётся в «Истории версий»). Справочник контрагентов и журнал КП не грузятся целиком:
поиск и страницы — на сервере (`/api/clients?q=&limit=`, `/api/history?limit=&offset=&q=&author=`). Каталог, менеджеры,
поставщики и категории отдаются с `ETag`: браузер перекачивает их, только когда они изменились.

Проверка контрагента (Checko: бесплатно 100 запросов в календарный день по Москве, полная проверка — 4 запроса).
Запросы считаются на весь отдел (kv `checkoQuota`, по `meta.today_request_count` из ответа Checko); лимит меняется
в «Интеграциях» (`checkoDaily`). Реквизиты по ИНН — из DaData и ФНС ЕГРЮЛ (Checko — только запасной источник);
повторная проверка берёт годовую отчётность из прежней (до 120 дней). Осталось 1–3 запроса — краткая проверка
по карточке Checko; лимит исчерпан — бесплатная по ФНС ЕГРЮЛ / DaData со ссылками на суды, ФССП, «Прозрачный бизнес»,
Федресурс. В обоих случаях ИНН попадает в очередь (kv `checkQueue`), и полная проверка выполняется сама после
обновления лимита (раз в 30 минут, последние 20 запросов дня остаются для проверок вручную) — результат попадает
в кэш проверок и в карточку клиента.

Доставка по России (`web/js/features/logistics-calc.js` — расчёт, `logistics.js` — вкладка «Логистика» в «Экономике сделки» и «Настройки» → «Логистика»; тарифы можно скачать шаблоном CSV и загрузить файлом .xlsx/.csv с предпросмотром изменений).
Груз — масса и габариты из характеристик позиций («Масса», «Вес брутто», «Габариты Д × Ш × В», «Ш × Д × В», отдельные
«Длина / Ширина / Высота»; мм, см, м); недостающее вписывается в окне расчёта. Откуда — склад поставщика (поле `wh`
в справочнике поставщиков; для импорта по умолчанию — город СВХ из тарифов), куда — адрес объекта. Расстояние — по
встроенной таблице городов и регионов: по прямой × коэффициент дорог (европейская часть / Урал и Сибирь / восточнее
Байкала). Машина — самая дешёвая из тарифов, куда помещается груз (раскладка по длине площадки, без штабелирования);
не помещается — несколько машин. Негабарит по ПП РФ № 2200: ширина > 2,55 м или высота > 4 м от дороги — спецразрешение
и надбавка к ставке; тяжеловес — разрешение и плата за вред дорогам; шире 3,5 м — прикрытие. Тарифы — kv `logistics`,
`/api/logistics` (изменение — только администратор); стандартные ставки — рынок РФ 2026 (ATI.SU «Средние ставки», тарифы транспортных
компаний, госпошлина 1 600 ₽ за спецразрешение, вред дорогам по ПП РФ № 67; список — `LG_DEFAULTS.sources`), уточняются
по счетам перевозчиков. Вписанные в расчёте масса и габариты записываются в характеристики позиции КП и в карточку каталога
(`lgWriteCargo`: в строку, из которой прочитаны, иначе — в группу «Габариты и масса»). Каждое предложение приводится к «дверь в дверь»: база перевозчика (`base`; у межтерминальных — плюс
забор и доставка по городу по тарифам), агент-экспедитор `agentPct` (по умолчанию 15 %) — только для отдельной машины
(ATI.SU) и расчёта по тарифам, у транспортных компаний комиссии агента нет; обязательное страхование: перевозчика (`ins`
в предложении — по объявленной стоимости: ПЭК `strah`, Деловые Линии `cargo.insurance.statedValue`, Энергия
`declaredCargoPrice`, СДЭК услуга `INSURANCE` через `/calculator/tariff`, Возовоз `cargo.insurance`, КИТ строки
«страхован…» в детализации), а если перевозчик его не посчитал — своё `insPct` % от стоимости груза (закупка позиций, не
меньше `insMin`); и разгрузка. В сделку — выбранное предложение (`s.lg.pick`) или максимальное.

Поля дат (`web/js/ui/datepicker.js`) открывают свой календарь: выходные, праздники ст. 112 ТК РФ, переносы и сокращённые дни
по производственному календарю (`/api/calendar`, поле `short` — сокращённые предпраздничные дни).

Цены перевозчиков (`app/logistics_api.py`, `/api/logistics/quote`): ATI.SU «Средние ставки»
(`api.ati.su/priceline/license/v2/all_directions` и `average_prices`, ключ `atiToken`, платная лицензия) — отдельная
машина, верхняя граница (`UpperPrice`) за рейс или ₽/км × км; ПЭК (открытый калькулятор `calc.pecom.ru`, без ключа),
Деловые Линии (`api.dellin.ru/v2/calculator.json`, `dellinKey`), КИТ (`capi.tk-kit.com/2.0/order/calculate`, тариф `01`, `pick_up`/`delivery` = 1, города — `/1.1/tdd/city/get-list` и `/1.1/tdd/search/by-name`, `kitToken` — Bearer), СДЭК (`api.cdek.ru/v2`: OAuth `cdekId` + `cdekSecret`,
`calculator/tarifflist`, только тарифы «дверь — дверь», `delivery_mode` 1), Возовоз (`vozovoz.ru/api/`, объект `price`,
`vozovozToken`), Энергия (открытый `api2.nrg-tk.ru/v2/price`, без ключа; забор и доставка прибавляются) —
сборный груз, если места не больше 3 т и 6 × 2,4 × 2,5 м. Итог — максимальное полное предложение (вместе с расчётом по
тарифам) со сноской. Справочники городов перевозчиков кэшируются на 7 дней (kv `lgdict:*`); нет города — ближайший крупный.
Автообновление (`auto_refresh`, раз в 3 часа проверяет срок): ставки ₽/км классов машин — максимум верхних границ ATI.SU по
опорным направлениям за период; результат — kv `logisticsAuto`, подставляется в классы с «Авто». Форматы API взяты из
документации и SDK перевозчиков; ошибки ответа показываются в окне расчёта как есть.
Ключи вводятся прямо во вкладке «Настройки → Ключи API» (`keysForm` в `clients.js`, `PUT /api/integrations`). Резервная копия ключей —
`GET /api/integrations/export` (только администратор); шифрование паролем делает браузер (Web Crypto: PBKDF2-SHA256, 250 000
итераций, AES-256-GCM), сервер файл не хранит; восстановление — тот же `PUT /api/integrations` с отмеченными ключами.

Точные адреса (`app/geo.py`, `/api/geo/suggest|locate|reverse|route|unshort`, поле `web/js/ui/geo-input.js` для любых
`input[data-geo]`): подсказки DaData `suggest/address` (с ключом DaData) или OpenStreetMap Nominatim (без ключа, не чаще
1 запроса в секунду); координаты по точке — DaData `geolocate` или Nominatim `reverse`; расстояние по дорогам — OSRM
(`router.project-osrm.org`), кэш kv `georoute`. Короткие ссылки раскрываются только для доменов Google и Яндекс Карт.
Точка склада хранится у поставщика (`whGeo`), точка объекта — в расчёте (`s.lg.toGeo`), маршрут — `s.lg.route`.

Справочник поставщиков (`suppliers.doc`): помимо условий — `req` (реквизиты), `warehouses` [{name, addr, lat, lon, city,
hours, contact, phone, note}], `contacts`, `makers`, `items` (id позиций каталога). Правка — «Настройки → Справочники и
данные» (`web/js/features/settings-dir.js`); автосохранение условий из «Экономики сделки» эти поля не затирает. Базу нельзя класть в общую сетевую папку — для работы отделом
используется сервер отдела.

## Сервер отдела

На постоянно включённом компьютере: `server-setup/1. Установить сервер отдела.bat` (от имени администратора) —
режим сервера, порт в брандмауэре, общая папка `\\ИМЯ\КП` (чтение), автозапуск при включении, ярлык `.url` для сотрудников.
Сотрудники открывают `http://ИМЯ-КОМПЬЮТЕРА:17845/`. Общие: каталог, журнал, нумерация, контрагенты, шаблоны, типы, ключи API.
У каждого в браузере: черновик, контакты менеджера, выбранный шаблон. По сети КП скачивается («Скачать .docx»),
«Путь к файлу» копирует сетевой путь. Выключается сервер только на самом сервере.

Управление (`server-setup/kp-server.ps1`, общая часть — `install/kp-common.ps1`, `Stop-KP` / `Start-KP`):
`2. Остановить сервер.cmd` — `POST /api/shutdown` (принимается только с самого компьютера), `schtasks /End`, затем
`taskkill /T /F` для всех процессов программы: по имени EXE и папке через WMI (видит процессы SYSTEM) и по владельцу
порта 17845; проверка, что ничего не осталось. `3. Запустить сервер.cmd`, `4. Удалить сервер отдела.cmd`.
Установщики полного комплекта и обновления используют ту же остановку; сборка проверяет «остановить — запустить —
остановить» на Windows.

Задача Планировщика (автозапуск): `schtasks /Create … /SC ONSTART /RU SYSTEM /RL HIGHEST`, затем `Set-KPTask`
(`install/kp-common.ps1`, `kp-server.ps1 -Action task`): без ограничения времени работы (`ExecutionTimeLimit PT0S` — по умолчанию
Планировщик ставит `PT72H` и останавливает сервер на третьи сутки), работа от батареи и ИБП (`DisallowStartIfOnBatteries`,
`StopIfGoingOnBatteries` — false), обычный приоритет (5 вместо 7), 3 повтора запуска раз в минуту. То же задают установщики
полного комплекта и обновления, а программа в режиме сервера на Windows проверяет задачу при запуске и исправляет её сама
(`app/server_task.py`, `ServerTask`: PowerShell `Get-ScheduledTask` / `Set-ScheduledTask`, итог — kv `serverTask`,
«Система» — строка «Автозапуск», «Требует внимания» — если исправить не удалось). CI создаёт задачу как прежние установки
и проверяет исправление установщиком и самой программой, запущенной задачей от имени SYSTEM.

## Возможности

- **Клиент:** реквизиты по ИНН, справочник контрагентов (объекты, контактные лица), проверка Checko (в КП не выводится).
  Загрузка клиентов списком ИНН (`app/web/js/features/clients-import.js`): вставка из Excel или файл .xlsx/.csv/.txt →
  реквизиты по одному запросу с паузой (ЕГРЮЛ ФНС или Checko/DaData) → справочник; итог — CSV для Excel.
- **Оборудование:** быстрый поиск по каталогу, плитки видов оборудования, карточка позиции с вкладками
  (основное, состав станции, «Заполнить с ИИ», описание и фото, характеристики, опции), фото к блокам описания,
  схемы и чертежи, выбор главного фото из изображений позиции (миниатюры под фото или «★ Главное» на карточке
  изображения — прежнее главное уходит в изображения), дублирование позиций.
- **Категории оборудования** (`app/equipment_types.json`): ДГУ, осветительные мачты, сварочные генераторы; компрессоры —
  дизельные, винтовые, спиральные, поршневые, центробежные; подготовка воздуха — осушители адсорбционные и рефрижераторные,
  магистральные фильтры; вспомогательное оборудование — ресиверы, шкафы АВР; насосы; запасные части и ЗИП (вид, для какого
  оборудования и производителя, двигатель/узел, модели, артикул, оригинал/аналог, интервал замены); прочее. У каждой
  категории свои параметры (по группам), фильтры, быстрые опции и шаблон таблицы характеристик; поле `find` —
  из какой строки таблицы характеристик берётся значение параметра.
- **Обновление каталога** (`app/catalog_migrate.py`): при первом запуске новой версии — копия базы в `data/backup`,
  перенос позиций в новые категории, заполнение параметров из характеристик, фото от похожей модели того же
  производителя для позиций без фото; итог — в окне «Каталог обновлён». База не заменяется, меняются только записи каталога.
- **Каталог** (`features/catalog-window.js`, `features/catalog-edit.js`): дерево категорий и фильтры по параметрам типа,
  список с отметками, карточка-предпросмотр (фото, параметры, описание, характеристики, история цен). Правка позиции
  каталога в той же карточке, что и позиция КП, плюс цена в каталоге. Пакетно: добавить в КП, перенести в категорию
  (также перетаскиванием на категорию, с отменой). Новая категория — с параметрами похожей. Окно растягивается
  и разворачивается на весь экран. Импорт из Excel по шаблону, загрузка и выгрузка каталога — меню «Ещё».
- **Менеджер:** справочник менеджеров в базе (общий для отдела, таблица `managers`): выбор из списка, новый менеджер,
  правки контактов сохраняются автоматически; устройство помнит выбранного менеджера.
- **Условия:** стандартные условия плюс «Дополнительные условия и оговорки» — свободный текст под условиями в КП.
- **Оформление КП** (бывший «Титульный лист»): живое превью первой страницы КП с фото оборудования, выбор фото на титул.
- **Предпросмотр и PDF:** «Предпросмотр КП» — документ целиком в окне, без скачивания (`vendor/docx-preview`).
  PDF создаёт компьютер-сервер (`app/pdf_convert.py`): Microsoft Word, иначе LibreOffice, иначе облачный ConvertAPI
  (ключ — «⋯» → «Настройки» → «Ключи API»); галочка «Также сохранить в PDF» кладёт PDF рядом с .docx. Если ничего нет —
  печать из предпросмотра → «Сохранить как PDF».
- **Цены:** валюта КП, курсы ЦБ РФ (cbr.ru, резерв — cbr-xml-daily.ru); одна строка на позицию: цена за единицу с НДС (вручную),
  скидка, сумма. Закупка и подбор цены под маржу — в «Экономике сделки» (крупная кнопка в разделе).
  Скидка для заказчика по позиции (% или сумма на ед.): в КП — колонка «Скидка», «Сумма без скидки» / «Скидка», на титуле «с учётом скидки»;
  итоги — после скидки. Вывод скидки в КП включается в шаблоне (блок «Показывать скидку для заказчика»).
- **Титул:** одна или несколько моделей, получатель, объект, дата; выбор шаблона КП (настройка шаблона — в «Настройках»).
- **Типы оборудования:** `app/equipment_types.json` + свои типы (меню «⋯» → «Типы оборудования»): параметры, фильтры,

  в двух независимых колонках (длинные значения — текстом во всю ширину; большая группа — пополам); небольшие позиции при большом числе
  страниц оборудования — карточками по нескольку на странице; титул всегда на одной странице (до 8 моделей — карточки с фото, больше —
  сводка по видам оборудования); без пустого последнего листа. Имя файла: `<номер>_<префикс шаблона>_<клиент>_<оборудование>_<дата>.docx`.

- **Работа менеджера (3.42):** «Мой день» при запуске (`features/my-day.js`), черновики на сервере и автосохранение,
  заготовки КП (`features/kp-drafts.js`), цены позиции в прошлых КП (`PriceHist` в `features/pricing.js`), окно «КП сохранено»

  Каждая — функция программы: включается и выключается, доступ — всем, администратору или выбранным менеджерам.

- **Телефон** (`css/mobile.css`, `js/ui/mobile.js`, Safari iOS и Chrome Android): шапка с кнопкой «Меню» (новое КП, журнал,
  каталог, предпросмотр, тема, «Настройки»), шаги КП строкой вверху, внизу — «‹ назад», итог и «Далее» (на последнем шаге —

## Экономика сделки

Окно «Экономика сделки» (`app/web/js/features/deal.js`, расчёт — `deal-calc.js`, Excel — `deal-xlsx.js`) открывается крупной
кнопкой в разделе «Цены», из правой панели, журнала («⋯» → «Экономика сделки») и меню телефона. Здесь вводится закупка и подбирается
цена продажи; на документ КП расчёт не влияет (хранится в КП как `deal`), цены позиций меняются только кнопкой «Перенести цены в КП».
Пересчёт — при каждом вводе; у полей — пояснения «?». Каждый шаг — отдельная карточка; окно растягивается за правый нижний угол, «⤢» — на весь экран.

0. **Кратко** (открывается первой, `dlOverview`): вердикт (прибыльна / убыточна / чего не хватает — по статусам шагов `dlStepInfo`
   со ссылками), цена, прибыль, маржинальность, чистая прибыль; лента «Поставщики и сроки» — производство (0 → готовность) и доставка
   (→ у заказчика) каждого поставщика, ПНР, оплаты заказчика, ось в днях или датах; «срок изделия» — самая долгая поставка;
   своих денег на пике, когда вернутся, стоимость денег.
1. **Закупка.** Карточка поставщика: название и страна — поле со списком: ввод по первым буквам или выбор кнопкой «▾»
   (стрелки и Enter); в списке — поставщики из справочника и производители позиций.
   Страна задаёт таможню и валюту: Россия — без таможни, с НДС поставщика (переключатель «Цены в счёте: с НДС / без НДС»);
   Беларусь, Казахстан и др. ЕАЭС — без пошлины, НДС при ввозе к вычету; остальные — расчёт по ТН ВЭД.
   Цена закупки за единицу каждой позиции — в валюте счёта (хранится у позиции: `cost`, `costCur`, сохраняется в каталоге).
   «Сроки поставки» (изготовление, доставка до заказчика, лента дней), «Оплата поставщику» этапами (доля, событие:
   при заказе / перед отгрузкой / после поставки / после ПНР, + дни; последний — остаток) и «Стоимость перевозки»
   (до границы РФ, по России до объекта); «Ещё расходы»: прочая закупка, страхование,
   комиссия за перевод, брокер/СВХ, НДС к вычету. Поставщиков несколько — у позиции выбирается свой.
   **Справочник поставщиков** (таблица `suppliers`, `/api/suppliers`): поставщик с условиями сохраняется сам при вводе;
   в новом расчёте он подставляется по названию или по производителю позиций (поле `makers`).
2. **Таможня и ввозные налоги** — по позициям: код ТН ВЭД и ставка пошлины. Порядок поиска: вручную в этом КП →
   по модели каталога (`item:<id>`) → по категории (`cat:<тип>`) → справочное значение (`TnVed` в `tnved.js`: код из 10 знаков
   и ставка ЕТТ ЕАЭС по виду оборудования и характеристикам; надёжность — «справочно», «справочно · проверьте», «справочно · уточните»).
   Исправленный код у модели каталога сохраняется в базе (таблица `customs`, `/api/customs`) для следующих сделок;
   «Справочник кодов по категориям» — код и пошлина для каждой категории (можно изменить, «↺» — вернуть справочное) и свои
   категории («+ Добавить категорию», ключ `cat:x_…` с названием); у позиции — «из справочника…» подставляет код и ставку категории.
   Расчёт показан наглядно: таможенная стоимость → пошлина, сбор, НДС при ввозе → «Платим на таможне» и сколько из этого
   идёт в себестоимость. У каждого шага внизу справа — итог шага. Таможенная стоимость = оборудование + логистика
   до границы + страхование (распределяются по цене позиций); пошлина — по позиции; сбор — по шкале ПП РФ № 1637
   (`CUSTOMS_FEES`); ввозной НДС = (стоимость + пошлина) × 22/10/0 % — к вычету. Режимы: «Рассчитать», «ЕАЭС»,
   «Сумма целиком» (ввозной НДС пустой — неизвестен, прибыль коридором), «Нет».
Умолчания: поставщик — «Россия» (без таможни, НДС к вычету); дата договора — сегодня (`d.startAuto`: пока не указана вручную,
   сдвигается на текущий день, в шапке — «сегодня — уточните»). Готовые варианты оплат — `DL_SP_PRESETS` / `DL_TR_PRESETS`
   (выпадающий список по группам). Условия КП («Срок поставки», «Условия оплаты», «Монтаж, ШМР и ПНР», «Документация») —
   `dealCondSuggest`: текстом как в договоре; подставляются, пока поле пустое или не правилось вручную.
3. Монтаж и ПНР, прочие расходы, разработка документации (`d.doc`, виды `d.docK` = {pd, rd, id}; платёж — при готовности к отгрузке,
   строка `doc` графика; виды — в условие КП «Документация»); «Ещё»: резерв на гарантию и бонусы/комиссии (% выручки), прочий НДС к вычету.
   Банковская гарантия (d.bg): сумма — от аванса заказчика (оплаты до поставки), % цены или ₽; комиссия = сумма × % годовых ×
   дней / 365 (не меньше минимальной), платёж при подписании договора, в себестоимости (уменьшает налоговую базу).
   «Прочие расходы (наличные)» — необязательно: % от чистой прибыли (после налога, до этих расходов), % от выручки без НДС,
   % от суммы продажи с НДС или сумма на руки; «стоимость получения наличных, %» — расход K = на руки / (1 − %). Налоговую базу не уменьшают:
   налог = (R − C_total) × ставка; прибыль P = R − C_total − K; чистая прибыль = R − C_total − налог − K; маржа = P / R,
   наценка = P / (C_total + K). Выдача (xc.when): после последней оплаты заказчика (на финансирование не влияет)
   или частями с отмеченных оплат заказчика пропорционально их суммам (финансирование пересчитывается; от чистой
   прибыли — итерациями до совпадения; в Excel такие суммы графика — значениями, чтобы не было циклических ссылок).
4. Оплата заказчика этапами: название этапа, сумма в % или ₽, когда (после подписания / готовности / поставки / ПНР + дни);
   последний — остаток; шаблоны «100 % после поставки», «Аванс 30 %», «30 + 60 + 10 %» и др.
5. Цена КП и валюта: цены позиций, валюта КП, НДС и курс ЦБ меняются прямо здесь — сразу в КП;
   «Прикинуть другую цену» — только для расчёта.
6. Деньги и налог: стоимость денег — ключевая ставка ЦБ (`/api/cbr/keyrate`) + 3 п.п. годовых / 12, налог на прибыль.
7. График платежей — только рабочие (банковские) дни: производственный календарь РФ `/api/calendar?year=` (`app/workcal.py`:
   isdayoff.ru, резерв xmlcalendar.ru, хранится в базе, обновляется раз в 30 дней; без связи — выходные и праздники ст. 112 ТК РФ);
   дата платежа, выпавшая на нерабочий день, переносится на ближайший рабочий.
   График платежей с остатком денег и финансированием (простой процент, месяц = 30 дней); день строки можно изменить. Дата отсчёта (подписание договора, день 0) вводится вручную;
   у каждой строки — день и дата, они пересчитываются друг через друга; даты попадают в Excel.

Справа — **«Цена продажи»**: цель (маржинальность, наценка, прибыль или чистая прибыль) → цена КП с НДС и цена каждой
позиции (распределение пропорционально закупке — одинаковая наценка), «Перенести цены в КП», безубыточная цена.
Ниже — итог при текущей цене КП: прибыль, чистая прибыль, маржинальность, наценка, НДС к доплате, структура себестоимости.

- Формулы: R = S / (1 + v/100); себестоимость = прямые платежи − НДС к вычету + финансирование; прибыль = R − себестоимость;
  наценка = прибыль / себестоимость; маржинальность = прибыль / R.
- **«Excel для согласования»**: лист «Сводка» на одну страницу для коммерческого директора (показатели, вывод, позиции

  подписи «Подготовил» и «Согласовано»; печатается на одном листе A4), лист «Расчёт» с формулами (жёлтые ячейки — исходные данные) и «График платежей».
- Будущий модуль логистики заполняет логистику поставщика функцией `dealSetLogistics(id, {abroad:{v,cur}, ru:{v}, ship})`.

### Фиды поставщиков (`app/feeds.py`)

Настройки → «Фиды поставщиков». Фид — адрес YML-выгрузки (`<yml_catalog><shop><categories>…<offers><offer>`), например
`https://www.remeza.org/bitrix/catalog_export/yandex_202475.php`. Скачивается программой (защита от SSRF — как у загрузки
фото, до 150 МБ, кодировка из XML-заголовка, `<!ENTITY>` отклоняется), разобранный фид кэшируется на 30 минут.

- **Проверить фид** — сводка (позиций, в наличии, с ценой, с остатком, с фото, уже в каталоге), разделы фида с
  предложенной категорией каталога (её можно сменить или выбрать «— не загружать —»; выбор сохраняется), частые
  параметры, пример позиции.
- **Загрузить в каталог** — в фоне (прогресс на экране): позиция `<id фида>-<offer id>`; поля: `name` (или
  typePrefix+vendor+model), `vendor`, `model`/`vendorCode`, `barcode`, `description` (HTML → текст), все `param` → группа
  «Характеристики» и атрибуты фильтров (через `catalog_migrate.fill_from_name`/`fill_attrs`), `weight`, `dimensions`,
  `picture` (до 8 фото, повторно не скачиваются), `price` → РРЦ. Модель — `<model>`, иначе из названия (без слов типа и
  бренда), иначе артикул; параметр «Название, ед.» делится на название и единицу; «5,5+5,5» кВт → общая мощность.
  Категория программы — по названию позиции (разделы фида бывают подборками), раздел «Запчасти» → запасные части;
  в проверке фида для каждого раздела видно распределение по категориям, раздел можно сопоставить вручную. Цена продажи = РРЦ, пока её не поменяли вручную
  (`priceSrc`); закупка = РРЦ − «наша скидка», если скидка задана (`costSrc`). Ручные правки названия, описания и
  характеристик сохраняются (сравнение с тем, что пришло из фида в прошлый раз, — `doc.feed.orig`).
- **Категории** — только существующие: `item_cat` — раздел «Запчасти», явные правила `NAME_RULES` (медицинские → поршневые,
  фильтроэлементы/корпуса/патроны/поршневые детали → запчасти, циклонные сепараторы → фильтры), `PATH_RULES` по разделу
  сайта из «хлебных крошек» страницы (`doc.feed.crumbs`), определение по названию, `PATH_RULES` по разделу фида. Категория, назначенная правилами, хранится в `doc.feed.catAuto`: при повторной
  загрузке меняется, только если её не правили вручную. После обновления программы `feeds.upgrade` один раз перезагружает фиды.
- **Остатки по складам и параметры вместо тегов** (фиды Битрикса, например Сибторгсервис — Dali, CrossAir): параметры
  «Склад Новосибирск», «Склад Москва» — остаток склада, позиция получает «в наличии N шт.» с разбивкой по складам; если склады
  есть в фиде, позиция без них — «нет в наличии». «Бренд», «Модель», «Код номенклатуры» заменяют `vendor`, `model`, `vendorCode`.
- **Описания к фиду (JSON)** — у фида YML кнопка «Описания к фиду»: файл `{"format": "kp-feed-extra/1", "series": [{"cats": ["116"],
  "names": ["Двухступенчатые компрессоры"], "match": "шаблон названия", "mode": "empty|replace", "desc": [{"title", "text", "items"}]}],
  "items": [{"oid" | "url", "desc"}], "logos": {"марка": "data:image/png;base64,…"}}`. Описание серии получают позиции раздела
  без описания (`empty`) или все (`replace` — вместо рекламного текста сайта); описание позиции важнее серии и страницы товара.
- **Запчасти** (`spare_info`): «Вид» (`part`), «Для оборудования», «Подходит к моделям» (страница товара или серии из названия),
  «Артикул», «Производитель техники», «Оригинал / аналог», «Интервал замены» («замена каждые 4000 часов»).
- **Характеристики со страницы** (`page_props`): свойства schema.org `itemprop="additionalProperty"` (`<meta itemprop="name|value">`),
  иначе таблицы / dt-dd / блоки свойств Битрикса. «Название, ед.» → строка «Название» = «значение ед.». Поля категорий
  заполняет `fill_attrs` (в Python и `core/types.js`): сначала строка в единицах поля, иначе пересчёт л/мин ↔ м³/мин ↔ м³/ч;
  значения списков приводятся к вариантам категории («-40 °C» → «−40»). Пустые поля дозаполняют `CRUMB_ATTRS`
  (регенерация, привод, безмасляный — по разделу сайта) и `DESC_ATTRS` (по описанию). Кэш страниц — с версией `PAGE_V`.
- **Фид из файлов** (`app/feed_files.py`, `kind: "files"`) — для поставщика без YML: «+ Фид из файлов», затем два файла (хранятся в
  `data/feeds/<id>/pages.csv`, `price.xlsx`, загрузка `POST /api/admin/feeds/<id>/upload?kind=pages|price&name=…`, тело — файл).
  Парс сайта — CSV `категория, название, ссылка на страницу, картинки (« | »), описание, характеристики («Ключ: значение | …»)`;
  строки, обёрнутые Excel в кавычки целиком и с «;;;», и сломанные кавычки в описаниях разбираются без доверия CSV (`_split_line`).
  Прайс — книга XLSX с листами по сериям (`read_xlsx` на `zipfile` + regex: sharedStrings, inlineStr, объединённые ячейки
  разворачиваются); на листе ищется шапка «Артикул / Код SAP», «Модель» (полное название), «Название для печатной формы»,
  «Стоимость» (первый столбец без слов «опции/пуска/охл./рекуперации»), остальные «Стоимость …» — опции, прочие столбцы —
  характеристики с единицами из строки единиц; шапка из нескольких строк склеивается, повторы объединённых ячеек и название
  листа отбрасываются; цена группы в соседней строке без названия; «по запросу» → нет цены. Строка прайса для позиции парса —
  `match_prices`: полное название → без знаков препинания → код модели (`_model_key`) → «Название для печатной формы» → множество
  слов модели (`_model_set`, «EAGLE-N VSD 132 7,5 BAR» = «EAGLE-N 132-7,5 VSD»). `build_feed` отдаёт тот же словарь, что `parse()`
  для YML (`cats`, `offers`, плюс `match` — сводка сопоставления), поэтому предпросмотр, загрузка и проверка общие; `priceOnly` —
  строки прайса без страницы тоже становятся позициями (разделы «Прайс / <название листа>»). `priceKind`: `cost` — цена прайса →
  `doc.cost`/`costCur` (`costSrc = feed`, минус `discount`), РРЦ и цена КП не трогаются; `rrc` — как у YML. Опции прайса — блок
  `features[].feedOpts` «Опции по прайсу поставщика». Описание со страницы чистится `clean_desc` (абзацы, подзаголовки, «• …»,
  без рекламы и повторов); характеристики — `merge_specs`: строки парса + прайса, одинаковые параметры (`spec_class`: давление,
  производительность, мощность, габариты, масса, шум, выход воздуха…) берутся из прайса, поля категории выставляются заново
  (`_redo_attrs`, предложение помечено `authoritative`). Уже имеющиеся позиции того же производителя (`_existing_index` /
  `_link_existing`: производитель + модель, иначе название) не дублируются: к позиции привязывается один вариант серии (с тем же
  давлением), остальные варианты не создаются (`f.variants`); у позиции, заведённой вручную (`doc.feed.linked`), значения
  с цифрами заменяются в её таблицах по классу параметра (`_apply_rows`), остальные строки — группой «Данные поставщика»,
  описание и `flow`/`pressure` не трогаются. Наличие — только из файла остатков (`stock.xlsx`); без него `nostock`: `doc.stock`
  не пишется, пропавшие из парса только перечисляются в журнале. Прайс с несколькими таблицами на листе (АСО: фильтры, затем
  осушители) читается по шапке каждой таблицы (`_price_block`), строки-разделы на всю ширину — `group`, сноски «r - …» пропускаются;
  составные столбцы «Габариты / Масса / Упаковка» с единицами «см / кг / r (ü)» делятся на строки (`_spec_split`). Характеристики
  сайта с единицей в названии («Давление, атм.», «Габариты, см») приводятся `_spec_rows`: единица — в значение, сантиметры — в мм,
  «Привод 2,2 / 380» → мощность и напряжение, подписи прайса и сайта — общие (`SPEC_RENAME`). JSON-парс без категории — раздел по
  адресу страницы (`_url_cat`), «schemes» — в конец галереи, модель — код из названия. Автопроверка раз в день не применяется; «Обновить цены из прайса» = `check_feed` по
  сохранённым файлам. Ручная цена/закупка в редакторе помечается `priceSrc`/`costSrc = manual` и фидом больше не меняется.
- **Фото со страницы** — только из галереи карточки товара: блок `div.product-detail-gallery__slider--big`, ссылки
  `a.product-detail-gallery__link` (data-fancybox="gallery") на оригиналы, до 8; на сайтах другого шаблона — только ссылки
  `a[data-fancybox="gallery"]`, нет галереи — нет фото. Галерея страницы заменяет `<picture>` фида; фото не из галереи,
  загруженные раньше и не правленные вручную, при перезагрузке убираются.
  Фото, уже стоящее в позиции (в изображениях или выбранное главным в редакторе), повторно не добавляется.
  Страницы и картинки запрашиваются как из браузера (заголовки Chrome, cookie сайта, Referer, повтор при 403/429/5xx);
  ответ без признаков карточки товара (`<h1>` + schema.org/галерея) — ошибка, а не пустая страница в кэше. Итог загрузки —
  `photos {new, pages, items, multi, avg}` в журнале фида. Для одной позиции — `POST /api/pagephotos {url}` (кнопка
  «Фото с сайта поставщика» в редакторе).
- **Описание со страницы товара** (по умолчанию включено, «Описание, фото и применимость — со страницы товара»): при загрузке
  открывается `url` товара из фида, берётся элемент `itemprop="description"` (Битрикс: `div.detail-text-wrap`) — текст
  с абзацами и списками, без скриптов, шаблонов `#…#` и абзацев-призывов сайта (телефоны, «оставьте заявку», адрес сайта). Идёт в карточку, если длиннее описания из фида. Кэш — kv
  `feeddesc` на 30 дней, не больше 3 страниц одновременно; недоступные страницы — в журнале загрузки.
- **Проверка РРЦ и наличия** — раз в день после 6:00 (если включена «Раз в день проверять…» и из фида что-то загружено)
  и по кнопке: `doc.rrc {price, old, prev, prevAt, at}`, `doc.stock {qty, available, gone, at}`. Остаток — из `count` /
  `quantity` / `stock`, `outlets/outlet@instock` или параметра «Остаток/Наличие»; без количества — по `available`.
- Журнал (последние 30): изменения РРЦ в процентах, остатки, пропавшие и новые позиции, ошибки. Действия пишутся в
  журнал действий (`import_feed`, `check_feed`).
- В каталоге — значки «РРЦ ▲/▼» и остатка; в КП у цены — «Ниже РРЦ на X %» / «Выше РРЦ» / «По РРЦ».

Модерация: флаг `settings.productEditModeration {enabled, updatedAt, updatedBy}`. Когда она включена, правка товара
пользователем уходит в очередь (в каталоге — значок «На модерации»), а в каталог попадает после одобрения. Цены,
обновлённые при сохранении КП, проходят без модерации.

Пользователь определяется по выбранному менеджеру (заголовки `X-KP-User-Id` / `X-KP-User`) — это подпись, а не вход.
Защита от чужих сайтов, открытых в браузере сотрудника: изменяющие запросы (POST/PUT/DELETE) с чужим заголовком
`Origin` отклоняются (403); локальная программа отвечает только на имя `localhost`/`127.0.0.1`/`[::1]` (подмена DNS).
Серверу отдела можно задать в `settings.json` список `"allowedHosts": ["kp-server", "kp-server.company.local"]` — тогда
запросы с другим именем сервера тоже отклоняются. Тело запроса — не больше 300 МБ; `/api/img` принимает только JPEG/PNG/WebP;
ответы с `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`.

Вход администратора — cookie `kp_admin` (HttpOnly, SameSite=Strict) + заголовок `X-CSRF-Token`; пароль хранится как
хеш scrypt (резерв — PBKDF2) в базе.

## Шаблоны КП

Всё, что определяет документ, лежит в папке шаблона `templates/<шаблон>/` и правится без пересборки программы:

| Файл | Что в нём | Чем править |
|---|---|---|
| `template.json` | цвета, шрифт, стили текста (размер, цвет, начертание), все надписи с `{метками}`, порядок и включение разделов и блоков, правила раскладки, образец имени файла, тексты «О компании» | окно «Настроить шаблон» (или Блокнот) |
| `skeleton.js` | скелет документа — раскладка страниц: титул, «Наши клиенты», оборудование, таблица цен, условия, контакты, колонтитул | Блокнот (для новых блоков и компоновки) |
| `editor.json` | форма окна «Настроить шаблон»: вкладки, поля, подписи, подсказки | Блокнот |
| `base.docx` | шапка страницы, поля, размер листа, стили Word; ширина таблиц КП берётся из полей | Word |
| `clients*.jpg`, `hdr_logo_*`, `img_*` | «Наши клиенты», логотип шапки, свои картинки шаблона | графический редактор |
| `sign.png`, `stamp.png` | подпись и печать (тендерный шаблон) | «Настроить шаблон» → «Подпись и печать» |

**Графический редактор шаблона** («Настройки» → «Шаблоны и категории» → «Графический редактор», только администратор,
`app/web/js/features/template-designer.js`): документ собирается с `design: true` — скелет помечает прогоны стилем Word
`KPS_<стиль>`, картинки — `KPI_<правило ширины>`, начало раздела — абзацем `KPSEC_<раздел>`; docx-preview превращает их
в классы, по которым щелчок выбирает стиль/картинку/раздел. Свойства пишутся в `template.json`: `styles`, `texts`, `rules`,
`sections`, `blocks`, `colors`, `brandParts`, `font`, а также новые `page` (поля, см), `header` (шапка из настроек: логотип,
строки реквизитов, цвета, линия — заменяет шапку base.docx) и `images` (свои картинки `{id, file, place:'<раздел>Top|End',
widthCm, align}`). Свободное размещение: свои картинки (`images`, `float: true`) и надписи (`labels`) выводятся плавающими объектами Word
(`wp:anchor`, надпись — текстовая рамка `wps:wsp`) в крошечном абзаце привязки (стиль `KPFLOAT`; в редакторе — `KPANC_<место>`):
`x` — от левого края текста, `y` — от абзаца привязки, см. docx-preview надписи не рисует — `renderDocx` отдаёт список
`blob.kpFloats`, и `renderDocxInto` дорисовывает их во всех предпросмотрах. Размер картинок макета без пропорций —
`imgSize: {ключ: {w, h}}`, сдвиг текстов и картинок макета мышью — `para: {стиль | 'IMG_'+ключ: {align, indent, before, after}}`
(прибавляется к отступам абзаца, у которого первый текст этого стиля). Картинки загружаются в папку шаблона (`clients_*`, `hdr_logo_*`, `img_*`). «Сохранить как новый…» —
копия папки + новые настройки. Без входа администратора редактор не открывается (запись файлов шаблона — admin-only на сервере).

**Тендерный шаблон** (`templates/tender/`, «Тендерный (без графики)»): строгий документ без графики — бланк с реквизитами
(`company`, `letterhead`), исх. № и адресат, спецификация (производитель, модель, страна происхождения — из строки «Страна…»
характеристик, ед. изм., цена и сумма с НДС, элементы сборки и опции строками, итоги, прописью), условия, техническое описание
(описание, полная таблица «Наименование показателя — Значение показателя», состав сборки), сведения о поставщике (`supplier` —
пары «реквизит — значение», пустые не выводятся) и подпись. `features: ['header','kit','sign']`: с `'sign'` программа кладёт
в документ картинки `signImage` / `stampImage` из папки шаблона (`Min.sign`); подпись — на линии, печать — плавающим объектом у «М.П.»
(`rules.stampWidthCm`, `stampX`, `stampY`, `stampBehind`). Подписант — `signPost` / `signName`, пустое ФИО — менеджер КП.
Новые шаблоны из `templates/` раскладываются рядом с программой при запуске (`ensure_templates`), свои шаблоны не трогаются.

Окно **«Настроить шаблон»** («Настройки» → «Шаблоны и категории») строится по `editor.json`: цвета с палитрой, стили с образцом,
разделы стрелками ↑ ↓, «Пробный DOCX» по текущему КП до сохранения, история версий (`_history/`) с возвратом,
копия шаблона, заводской вариант. В программе остались только общие помощники (`app/web/js/docx/kpgen.js`: суммы прописью,
даты, итоги, загрузка скелета) и подготовка изображений (`app/web/js/docx/build.js`).

## Сроки в графике платежей

График — итог всех сроков «Экономики сделки». Дата платежа, изменённая в графике (перетаскивание строки, ↑ ↓ или ввод
даты), переписывает его источник (`dlSetRowDay` в `deal.js`): этап оплаты заказчика / поставщику — событие + дни
(если дата раньше события, этап переходит на ближайшее более раннее событие; рабочие дни считаются по календарю),
«Перевозка и сборы» — срок изготовления (`sup.prod`), «Доставка по России» и «Монтаж» — срок доставки (`sup.ship`).
Платёж без своего срока (комиссия банка за гарантию) получает дату вручную (`deal.days`).

Курсы ЦБ (`/api/cbr`) и ключевая ставка (`/api/cbr/keyrate`): удачный ответ сохраняется в базе (`kv`: `cbr_last`,
`keyrate_last`); если ЦБ недоступен — отдаётся сохранённый с `stale: true`.

## Планы (отложено)

**Счета, договоры и спецификации с 1С** — обсуждено, к внедрению позже. Исходные условия: счета и их номера создаются в 1С;
с частью клиентов уже заключены договоры, и по ним подписываются спецификации по установленной форме.
Предложение в три шага: (1) договоры клиента в карточке клиента и «Спецификация к договору» из сохранённого КП
(номер и дата договора, следующий номер спецификации, позиции, условия; для клиентов без договора — типовой договор);
(2) номер и дата счёта 1С в КП при статусе «Выиграно»; (3) обмен с 1С (HTTP-сервис, файл обмена CommerceML / Excel или
общая папка): заказ в 1С → счёт → номер и оплата обратно в КП. Нужно от заказчика: конфигурация и версия 1С, есть ли
HTTP-сервисы; образцы формы спецификации и типового договора; правило нумерации спецификаций; как связать номенклатуру
каталога с 1С; бывает ли несколько счетов на одно КП.

## Ключи API и безопасность

**Где хранятся.** Ключи Checko, OFData, DaData, перевозчиков и ConvertAPI вводятся в «Настройки → Подключения → Ключи API» и хранятся
только в базе программы (`data\kp.sqlite3`) на компьютере отдела. В EXE, репозиторий, журналы и историю изменений настроек они не попадают,
в окне показываются маской. Резервная копия ключей («Скачать ключи») — файл на вашем компьютере: храните его так же, как пароли.

**Проверка репозитория.** Сборка (`.github/workflows/build-exe.yml`, шаг «Проверка репозитория») запускает `.github/scripts/repo_guard.py`:
если в репозиторий попала база SQLite (`*.sqlite3`, `-wal`, `-shm` или файл с заголовком SQLite), выгрузка `kp*.zip` или строка, похожая
на ключ или токен, сборка останавливается со списком файлов. Локально: `python .github/scripts/repo_guard.py .`.

**История репозитория (проверено 10.10.2026).** Ключи Checko и DaData были только внутри файла базы `seed/data/kp.sqlite3`: он загружен
01.10.2026 (коммиты `b86ae00` и `95f57d9` «Add files via upload», вместе с `-wal`/`-shm`) и удалён 05.10.2026 (`6acf887`). Ещё одна база —
`samples/kp.sqlite3` (29.09–05.10.2026, `0a1b8e8` → `6acf887`). В текущих файлах и в EXE-выпусках ключей нет; репозиторий приватный,
доступ — только у владельца. Но старые коммиты хранят эти файлы целиком, поэтому ключи из них нужно считать раскрытыми.

**Что сделать.**
1. Сменить ключи в личных кабинетах сервисов: Checko (checko.ru — раздел API личного кабинета), DaData (dadata.ru — «API-ключи»: ключ и
   секретный ключ), OFData и перевозчиков — если их ключи тоже были в той базе. Перевыпущенный ключ делает старый недействительным.
   Новые ключи — в «Ключи API» → «Сохранить ключи» → «Проверить подключения».
2. По желанию — убрать старые базы из истории (в них были и данные клиентов). Делается один раз, когда нет незавершённой работы
   в ветках: все хеши коммитов изменятся, 52 метки выпусков переедут на новые коммиты, у всех копий репозитория нужно сделать новый клон.
   ```
   pip install git-filter-repo
   git clone --mirror https://github.com/DevMoreBill/KP.git KP-mirror.git
   cd KP-mirror.git
   git filter-repo --invert-paths --path seed/data/kp.sqlite3 --path seed/data/kp.sqlite3-wal --path seed/data/kp.sqlite3-shm --path samples/kp.sqlite3
   git push --force --mirror
   ```
   GitHub ещё какое-то время показывает старые коммиты по прямой ссылке — полностью их убирает служба поддержки GitHub
   (запрос «Remove sensitive data / cached views»). Выпуски (EXE) после переписывания истории остаются.

## Запуск из исходников (для разработки)

`python app/kp_server.py` — данные создаются в `app/`.

Проверки перед отправкой: `python tests/run_all.py` (около 2 минут; `--quick` — без фаззинга, обновлений и безопасности; имена
наборов — только они, например `python tests/run_all.py test_api`). Рабочая база не используется: стенд — во временной папке.
